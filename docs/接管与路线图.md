# 接管与路线图

## 产品目标

让其他作者从模板开始，构建一个插件，装入测试环境，查询明确的能力，并获得可诊断的加载结果。先完成《星界战士》基座，再依据真实需求决定其他游戏适配；不提前承诺跨游戏或跨平台。

原工程位于本机 dsh 应用数据目录，无远端仓库。基线 HEAD 为 bc509e7，存在未跟踪 minidump.py，本次完整保留该工具。用户已确认路线 1。正式源码已迁到用户 Documents/repo/astral-forge，保留原 Git 历史及 minidump.py；原 dsh 项目仍保留。验证期间临时部署候选，测试后已恢复游戏文件。尚无远端仓库或公开发布。

- 增加最小插件模板、独立构建脚本和中文开发指南。

## 按验收推进

1. **稳定加载底座**：定位真实游戏启动失败；验证纯加载入口与渲染入口的分工、超时与诊断。验收游戏正常启动、退出、重复启动，以及 BD 共存。当前不认为离线 Present 测试足够。
2. **可维护插件契约**：清单版本、依赖与冲突解析、按插件归属的回调/挂钩清理、初始化失败回滚、UTF-8 路径、配置数据归属。验收旧插件兼容、重复 ID、失败插件和生命周期测试。
3. **游戏适配层**：分离加载服务与 Astral Ascent 地址/对象知识；先提供只读玩家、房间和构筑查询，再提供有约束的修改命令。验收真实游戏版本指纹与精确状态变化。
4. **参考插件与 SDK**：一个只读状态显示插件和一个受控玩法插件，证明开发者无需再次逆向相同内容。补齐 API 文档、构建/打包/安装检查和持续集成。
5. **可选能力**：依据开发者需求决定 Lua 与资源替换；不同时建设所有宿主语言或完整 GUI Mod 管理器。

## 架构边界

沿用原生 C++ 与版本化 C ABI，渐进改造已有模块；这是库/运行时，不套用界面 MVC。依赖方向建议为插件 → 公共 SDK → 加载核心/游戏适配器/可选渲染模块。游戏适配器承载版本差异，核心不承载 BD 配方或具体玩法。

用户已确认先实施星界战士专用路线。采用渐进式模块边界，不执行全量重写；稳定加载与 SDK 的第一阶段结果见阶段验收。

## 发布门禁

离线测试、旧 ABI 插件、无渲染加载、真实游戏生命周期、BD 共存、包许可/负载审计均通过后才可公开标记可用。保护游戏存档与现有光环方案。第三方 research 源码不包含在 SDK 包中。明确区分能力实现、离线验证、实机验证和公开发布。

0.1.4-dev 已建立精确游戏身份、原生更新边界、只读引擎场景与玩家层内坐标快照，以及独立 state_watch 示例。当前阶段正常流程已通过：血量字段完成原生绑定及隔离差异验证，正常进入游戏、生成场景/战斗房间切换、敌人攻击致死、返回大厅及再次开局均有实机记录，原文件和存档回滚哈希一致。后续状态事件接口正在实现与验证。引擎 layout 不等同于程序生成房间。

## 当前阶段通过后的后续授权

用户已授权：当前阶段完成后，继续推进游戏事件、受控修改接口和资源扩展。按以下顺序实施，无需为同一范围重复请求确认；尚未通过的前置验收不能用离线测试或测试入口场景切换替代。

### 进入下一阶段的门禁

1. 验证玩家当前/最大血量的真实语义，区分未出现玩家、死亡、无效字段与暂停后的旧快照。
2. 在隔离存档中验收正常进入游戏、程序生成换房、死亡和重开，确认失效对象不会被跨帧读取；未知版本保持不可用。
3. 独立示例仅通过公共 SDK 查询，现有 ABI、插件关闭、加载/渲染、安装回滚检查通过，游戏原文件及原存档恢复且哈希一致。

### 游戏事件

先开放有真实证据的场景切换、玩家出现/消失及状态更新事件。明确事件来源、顺序、派发线程、订阅归属、关闭清理和积压策略。快照差分只能称为状态变化，不能据此宣称捕获原生受伤、击杀、拾取等语义事件；这些事件必须另行定位并验证原生触发点。用独立事件记录插件验证订阅、取消、重开和失败插件清理。

### 受控修改接口

在真实游戏更新线程消费有界命令队列，提供请求结果；逐项开放已验证的操作。命令明确参数范围、可用场景、目标和生命周期，过期目标或未知版本显式拒绝。不得把任意地址读写、原始对象指针或绕过版本检查作为稳定 SDK 契约。优先选择可在隔离存档中观测并恢复的最小操作，以独立玩法示例验证执行结果、重复请求及场景切换后的拒绝行为。

### 资源扩展

先确认真实资源索引、归档/加载路径、解码和释放归属，再选一种已验证资源类型完成加载与替换闭环。明确命名空间、路径边界、同资源冲突、格式/尺寸验证、缓存和释放时机；只能分发 Mod 自有资源及许可允许的依赖。用独立资源示例验收成功加载、无效资源诊断和重复场景切换后的释放。尚未验证的资源类型继续报告不可用，不因已有预留函数就开启能力位。

以上为已授权推进顺序和验收约束。新 C ABI 继续追加字段；每项通过对应验证后再更新能力声明及开发者文档。
